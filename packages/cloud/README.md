# `@comms/cloud`

Chirp Cloud is the full-stack Next.js dashboard and control plane. It always ships the browser application and backend together; there is no supported headless mode. Shared Effect schemas provide the typed browser/server contract, while server-only Effect services own durable work and provider access.

Cloud does not import board server or boot internals. A deployed board is an opaque, versioned Chirp image operated through public behavior, with one immutable operator command for initial setup-code issuance. Cloud authentication never substitutes for a board session.

The control plane uses PostgreSQL for private board metadata, authentication, invitation consumption, and its leased operation queue. GitHub and Google OAuth create accounts only through single-use invitations; an authenticated user can then enroll a passkey.

Migrations run under one transaction-scoped advisory lock: DDL and its receipt commit together, and rerunning never rewrites a receipt. Migration ids start at 1 and are consecutive. Each migration declares a sorted, unique `compatibleSchemaVersions` list of older image schema versions it has been verified to preserve; an empty list permits no rollback across that migration. An image's schema version is its registry head. An older image may run only when its entire known ledger prefix matches and **every** newer applied migration explicitly lists that version. Missing or malformed receipts and unknown or incompatible newer schemas fail closed; a later compatible receipt cannot undo an earlier incompatibility.

Compatibility declarations are part of the immutable receipt, not an operator override. Do not edit historical migration names or compatibility lists after applying them, and do not delete receipts to force a rollback. This unmerged foundation changes the initial ledger format and corrects the names of constraints created by migration 1 in place because no released Cloud version has applied it. After the foundation ships, existing migration bodies are immutable and every schema change requires a new migration; a development database created from an earlier unmerged revision must be recreated rather than silently backfilled.

Copy `packages/cloud/.env.example` to `packages/cloud/.env.local`, generate `BETTER_AUTH_SECRET` from at least 32 random bytes, run `bun run --filter @comms/cloud migrate`, then run `bun run --filter @comms/cloud dev`. Configure at least one OAuth provider: set both `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`, both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, or both complete pairs. Leave the unused pair unset or blank; partial pairs are rejected. Login and invitation pages show only configured providers. OAuth callbacks use `/api/auth/callback/github` and `/api/auth/callback/google` on `BETTER_AUTH_URL`. Cloud sessions use a host-bound `__Host-` cookie, stay on that host, and never authenticate a board. Restart the development server after changing auth configuration because its managed request runtime intentionally survives Next.js module reloads.

Set `CLOUD_CLIENT_IP_HEADER` to one authoritative, single-value client address header written by the edge proxy; `fly-client-ip` is the Fly Proxy value. Authentication rejects missing, malformed, or multi-value headers rather than collapsing them into a global rate-limit bucket. The production listener accepts only IPv4 transport, which is the private address family Fly Proxy uses; direct Fly 6PN traffic is IPv6 and is refused before routing. Other deployments must preserve the same proxy-only boundary and replace rather than append or preserve a caller-supplied value. Better Auth uses this header for per-client rate limits and session metadata.

To issue a single-use invitation after migrations are applied, run `bun run --filter @comms/cloud invite`. The command prints the invitation fragment once; only its SHA-256 digest is stored. New invitations can be redeemed by anyone holding the link using a verified OAuth account. They expire after 24 hours and work once. Existing email-bound invitations retain their original email restriction; migration 11 only makes the email column nullable and does not rewrite existing invitations. Operators can also issue links through `POST /api/invitations` with same-origin JSON `{}`. Set `CLOUD_OPERATOR_EMAILS` to a comma-separated list of verified Cloud account emails allowed to invite; empty or missing configuration denies issuance. `GET /api/invitations` returns the authenticated account's `can_invite` capability. Successful issuance returns `{ "url": "https://…/invite#…", "expires_at": "…" }` once and sends no email. Operator issuance is capped at 20 links per account in a one-hour window, serialized with issuance in a database transaction. Its separate quota table survives invitation consumption and authentication rate-limit cleanup. CLI issuance remains an operator database-access command outside this HTTP quota.

The Next.js process owns bounded authentication and dashboard request runtimes, each with one shared pool capped at eight connections, and a separate scoped provisioning worker whose pool is also capped at eight. The existing request-runtime bridge shares those instances between the custom server and Next.js route bundles. The worker reconciles one deterministic Fly App, encrypted Volume, and Machine per board through direct API observation; a separate deletion worker removes the tracked Machine and Volume only after a confirmed owner request. The production server stops accepting requests, drains them, closes Next.js, and then awaits disposal of the worker and both request runtimes.

New boards receive a readable suggested name and an editable, globally unique address slug. `POST /api/boards` accepts optional `slug`: 3–32 lowercase letters, numbers, or hyphens, beginning and ending with a letter or number. If omitted, Cloud generates a readable slug. Board names remain independent display labels. The list response includes `boards_domain` for an accurate address preview. Creation rejects an unavailable address with `409 slug_unavailable` and invalid syntax with `400 invalid_slug`; idempotency covers the requested slug as well as the name and storage. Deleted boards retain their slug reservation. Existing board names, slugs, and hostnames are unchanged. Stop old workers before migration 10 and deploy this version before accepting readable slugs; older workers cannot provision their normalized Fly Volume names.

Each owner can create at most five boards, including queued and blocked boards. Board creation serializes per owner inside the database transaction before checking the quota and inserting the board and its provision operation. Idempotent retries still return their original board at the limit; new requests return `403 board_quota_exceeded`. Confirmed deletion frees a slot only after provider absence is verified (or immediately for never-claimed local boards). Deleting and blocked-deletion boards remain counted.

The dashboard lists up to the newest 100 owned boards in one bounded query, independently of the five-board creation quota. It reads one extra row to report truncation explicitly rather than silently hiding older running infrastructure; no cursor is exposed in this release. Board detail reads validate UUID identifiers and return the same 404 for malformed, missing, and foreign IDs. Creation checks the browser Origin against the configured `BETTER_AUTH_URL`, not proxy-derived request URLs.

Board status reporting prefers the authoritative terminal state over the last recorded error code. A failed operation or blocked deployment is reported as stopped and never claims an automatic retry; its recorded code is kept only for diagnosis. A pending provider observation, an unresolved ambiguous mutation, and an unreachable board address are reported as ordinary progress, because a board's first boot legitimately takes minutes and none of them spends the failure budget. The reported error is shown on the setup step its code names, which may be a step that was already confirmed and is being re-verified; a code that any step can raise stays on the next unconfirmed step and says that this is not necessarily where it failed. Definite provider rejections, immutable-resource drift, and exhausted retries are reported as needing an operator.

Managed SQLite needs no provider runtime secret. Once its Volume is ready, provisioning creates the Machine directly. PostgreSQL board creation accepts one administrator URL when `CLOUD_SECRETS_KEY` is configured. Cloud creates two databases and two restricted logins per board, verifies the boot/app separation, and stages only the derived board credentials in Fly Secrets before creating a Machine with the observed minimum secrets version. MySQL onboarding remains unsupported.

Migration 9 is not rollback-compatible. A pre-migration worker does not understand the PostgreSQL secret checkpoint and must never run after the new table is applied.

`CLOUD_SECRETS_KEY` is an independent 32-byte key encoded as 64 hexadecimal characters (`openssl rand -hex 32`). Back it up privately with the control-plane database; changing or losing it prevents decrypting queued and retryable board credentials. Administrator URLs and generated passwords are AES-256-GCM encrypted with a fresh nonce and authenticated board-ID context, committed with the board creation operation. Neither dashboard responses nor Machine configuration expose URLs. The administrator credential remains encrypted only until the idempotent bootstrap is durably confirmed; that fenced checkpoint atomically replaces it with the two board-scoped runtime URLs. Cloud does not use the administrator credential to delete external databases.

Use a direct PostgreSQL administrator endpoint with role/database creation privileges, not a transaction pooler. Cloud creates names derived from the board UUID and refuses unrelated existing roles/databases. Public IPv4 endpoints require verified TLS. `sslmode=require` and `sslmode=verify-full` are accepted and normalized to the board's query-free database URLs. `channel_binding=require` is rejected explicitly because the available drivers cannot enforce it; remove that parameter while retaining verified TLS to use this onboarding flow. Other query overrides are rejected. DNS addresses are checked and pinned for bootstrap connections; private, reserved and IPv6 addresses are refused. `CLOUD_POSTGRES_ALLOW_LOCAL=true` permits loopback endpoints only for isolated local tests, including `sslmode=disable`; do not enable it on hosted Cloud.

A PostgreSQL board still needs its source/data Volume. Provider-managed database snapshots and restores remain the database operator's responsibility. These tests establish local bootstrap/isolation and mocked Fly API contracts, not live provider connectivity. Fly secret staging uses the [Machines secrets API](https://docs.machines.dev/secrets/Secrets_update); Machines receive app secrets [as runtime environment variables](https://fly.io/docs/apps/secrets/).

Provisioning tracks worker claims separately from provider failures. Healthy readiness polls and ambiguous mutations do not spend the failure budget; they remain bounded by the operation's wall-clock lifetime. Actual transient failures retry with exponential backoff: a 5-second ceiling doubles to a 5-minute maximum, with each delay chosen randomly between half the ceiling and the ceiling. Ambiguous mutations wait at least 60 seconds, are recorded by resource, and are never issued again automatically while their result remains unobservable. Starting a Machine is the exception: it creates nothing, so repeating it cannot duplicate a resource and the Machine's own state is the observation of whether it took effect. A recorded `machine_start` is therefore retried rather than refused, and is cleared once the Machine is observed started. Definite provider rejections and immutable-resource drift block immediately. `PROVISIONING_MAX_FAILURES`, `PROVISIONING_MAX_AGE_MS`, and `PROVISIONING_POLL_INTERVAL_MS` default to ten failures, 24 hours, and 30 seconds. Reaching either durable limit blocks the deployment and fails the operation, releasing the board's active-operation slot. Resources are never deleted or replaced to recover.

### Operator recovery

Resolve the reported provider/configuration issue first. Inspect the failed provision operation's ID, checkpoint, error, and the deployment's current `row_version` using operator access to `CLOUD_DATABASE_URL`. Then run:

```sh
FAILED_OPERATION_ID=<failed-operation-uuid> EXPECTED_DEPLOYMENT_ROW_VERSION=<row-version> \
  bun run --filter @comms/cloud retry:deployment
```

This command requires control-plane database access; it is not a public or board-authenticated route. It atomically resumes the recorded checkpoint and queues one new operation with a fresh retry budget, retaining the failed operation and all deployment resource IDs, mutation markers, and snapshot records. Repeating the command for the same failed operation returns the existing retry rather than creating another. Stale row versions, active board operations, and superseded failures are refused. The worker checks the original immutable intent against its configuration and re-observes recorded resources before further work; a missing resource, replacement identity, incompatible configuration, or unresolved drift blocks again. Restore the original configuration/resource identity rather than editing IDs, changing storage engines, or recreating a missing Volume. This is a provisioning retry, not a data restore.

If provider inspection proves that a marked mutation never took effect, an operator can authorize only that mutation by adding a comma-separated `CONFIRMED_ABSENT_MUTATIONS` value to the same command. Allowed names are `app_create`, `volume_create`, `machine_create`, `machine_start`, `edge_ip`, `edge_certificate`, `edge_a_record`, and `edge_txt_record`. `machine_start` no longer needs this confirmation, because a recorded start is retried automatically. The command refuses names that are not recorded on the failed operation. This is an explicit duplicate-risk decision: do not clear a marker merely because an eventually consistent list is empty.

Stop old workers before applying the provisioning-recovery, provider-mutation-marker, and retry-budget migrations and deploying the new worker. They map the removed secret checkpoint to `volume_created`, preserve IDs and data, remove the unused secret-version and desired-revision columns, conservatively mark active or failed provider work whose result the old worker did not prove, and add a failure counter without rewriting claim history. A marker may require operator inspection after upgrade, but the new worker will not risk duplicating that resource.

## Deploying to Fly

`Dockerfile`, `fly.toml` and `dockerignore` in this package deploy the control plane; the repository-root `fly.board-image.toml` publishes the board image it provisions. The image build needs the repository root as its context and a separate ignore file, because the root `.dockerignore` describes the board image and excludes this package's fonts:

```sh
flyctl deploy --config packages/cloud/fly.toml --dockerfile packages/cloud/Dockerfile \
  --ignorefile packages/cloud/dockerignore --ha=false
```

`fly.toml` carries the values that identify one deployment: the app name, its region, the Fly organization boards are created in, and `BOARDS_DOMAIN`. Edit them to deploy a different instance. The machine keeps `auto_stop_machines = "off"` with one machine running because the provisioning worker reconciles boards between dashboard requests; a stopped control plane stops provisioning. `release_command` applies migrations before the new image serves.

Everything else is a secret: `CLOUD_DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, the OAuth pairs, `CLOUD_OPERATOR_EMAILS`, `FLY_API_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID` and `CHIRP_IMAGE`. Set them with `flyctl secrets import` rather than on the command line. The Fly token wants organization scope, not the deploying user's own credential.

`CHIRP_IMAGE` must be digest-pinned, so publish the board image first and record the digest the push reports:

```sh
flyctl deploy --config fly.board-image.toml --build-only --push --image-label board-<commit>
```

The control plane's own hostname needs a DNS-only `A`/`AAAA` pair at the addresses `flyctl ips list` reports and a certificate for it. Do not proxy those records: proxying breaks certificate validation and makes `CLOUD_CLIENT_IP_HEADER` report the proxy rather than the client.

## Managed board networking

Set `CLOUDFLARE_ZONE_ID` to the active `chirp.wiki` zone's 32-character ID and `CLOUDFLARE_API_TOKEN` to a token scoped to that zone with **Zone / DNS / Edit** and **Zone / Zone / Read** permissions. Cloudflare must be authoritative for the zone; do not delegate `boards.chirp.wiki` to other nameservers. `BOARDS_DOMAIN` defaults to `boards.chirp.wiki`; another domain must be inside the configured zone. The worker verifies the zone before changing DNS. Keep both provider tokens in the control-plane environment, never in board Machine environment variables or the database. The Fly token must allow app creation, shared public IP allocation, and certificate management in `FLY_ORGANIZATION`, in addition to Machines and Volumes.

Each app receives one shared public IPv4 assignment and an ACME certificate for its exact board hostname. The worker ensures a DNS-only `A` record at that hostname pointing to its assigned IPv4, and the app-specific `_fly-ownership.<hostname>` `TXT` record returned by Fly. It adopts matching resources and never updates or deletes existing DNS. Conflicting, proxied, duplicate, or delegated records prevent progress and are polled for operator repair until the operation lifetime expires; they are never permission to overwrite a record. TXT content may use Cloudflare's quoted representation.

An exact record is deliberate rather than `*.boards.chirp.wiki`: Fly requires ownership proof beyond a shared IPv4, and the per-host ownership TXT creates an implicit parent that suppresses wildcard answers on Cloudflare advanced nameservers. Fly also does not guarantee the same shared address for every app. Exact A records work on both Cloudflare nameserver types and allow independently assigned Fly addresses without rewriting a shared wildcard. Existing wildcard records are left untouched and are superseded only by each board's explicit record; no wildcard setup is required.

Networking is reconciled at `machine_started` and revalidated on recovery at every later checkpoint. Before publishing the route or probing HTTPS, Fly's fresh certificate check must report an active managed certificate, configured ownership, and the expected resolved A address with no AAAA override. DNS propagation, ACME issuance, and rate limits keep the operation queued rather than advancing `edge_reachable`. An ambiguous IP, certificate, A, or TXT write is observed on later attempts but never repeated automatically. The existing HTTPS `/health` and `/init` probes remain required. No additional database checkpoint or migration is needed. This runs for new and resumed operations, not as a background repair sweep of already-completed boards.

These contracts are from the [Machines OpenAPI reference](https://docs.machines.dev/openapi.json), [Fly certificates API](https://fly.io/docs/machines/api/certificates-resource/), [Fly custom-domain ownership requirements](https://fly.io/docs/networking/custom-domain/), [shared-IP routing](https://fly.io/docs/networking/services/), [Cloudflare DNS list](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/list/) and [create](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/) APIs, and [Cloudflare wildcard precedence](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/). Provider access and an authoritative active zone are operational prerequisites; mocked contract tests do not establish live provider credentials, delegation, or certificate issuance. Large rollouts must account for Let's Encrypt's per-registered-domain issuance limits.

### Managed snapshots

Managed SQLite Volumes enable Fly's automatic snapshots. Once the last observed completed snapshot is 24 hours old, the worker schedules an observation and records only the newest snapshot that Fly reports as completed, including its digest and observed retention. A failed observation releases the board operation slot and is retried on the next hourly schedule boundary. Chirp does not promise a retention period beyond that observation; Fly's current default is daily snapshots retained for five days when no explicit retention is configured. Provider completion and digest metadata do not prove SQLite consistency or restorability; no restore verification is implemented.

### Board deletion

`DELETE /api/boards/:boardId` requires the owner's Cloud session, the exact configured Origin, an `Idempotency-Key`, and `{ "confirmation_name": "Exact board name" }`. A never-claimed board is cancelled and tombstoned transactionally; its operation history and request keys remain reserved. Deletion of a deployed board queues durable work and returns HTTP 202 with its dashboard state. The board remains visible and counted against quota until Fly confirms absence. Active work and unresolved provisioning mutations refuse deletion; wait for active work or resolve provider uncertainty first.

The deletion worker checks the recorded App ID, organization, isolated network and board-derived name, and the recorded Machine/Volume IDs and identities. Unknown or changed resources block deletion. It destroys the tracked Machine and then the Volume; each retry observes current state first, and missing resources are idempotent success. The verified empty App is retained because Fly's App deletion endpoint is name-addressed and cannot bind the destructive request to the observed App ID. Deletion failures appear as `deletion_blocked`; after correcting the reported issue, confirm deletion with a new request key to retry. The same key only replays its own durable result. External PostgreSQL/MySQL databases are never dropped. Encrypted control-plane PostgreSQL credentials are purged in the same transaction that completes deletion; they remain available while deletion is pending or blocked. Managed Volume data is permanently removed; no restore workflow is provided.

Cloudflare records are retained because existing provisioning can adopt matching records without recording creation ownership. Deletion must not infer ownership from matching content. An operator may remove the exact obsolete board records after independently verifying ownership. Tombstones reserve board slugs so Cloud never reuses those hostnames. Stop old workers before applying migration 7; they do not understand deletion state.

### Initial board setup

`POST /api/boards/:boardId/setup-code` accepts exactly `{}` with the owner Cloud session and configured same-origin header. Once the deployment is ready and has no active operation, Cloud locks the board against deletion, verifies its recorded Fly App, organization, isolated network, Machine and complete configuration, and executes only `/usr/local/bin/bun /opt/comms/packages/boot/dist/setup-code.js`. A sleeping board is woken through its exact public `/health` URL and reverified. The command is an immutable, versioned image operator protocol, not an editable application command or a general exec API. It talks to boot's private root-only Unix socket; no board credential is passed to Cloud or the editable application.

The response contains `{ code, expires_at, onboarding_url }`, where expiry is an ISO timestamp and onboarding points to the exact board's `/onboarding` page. Each successful request creates a fresh code valid for fifteen minutes and invalidates earlier setup challenges. Codes are never stored in the Cloud database, logged, or placed in URLs. Responses are `no-store`. Concurrent issuance is refused using the board row lock; deletion waits until the bounded provider operation ends. After a board owner has enrolled a passkey, issuance returns `setup_closed` even if an operator has reopened recovery setup. This cannot reset or take over an existing board owner.

The deployed board image must include this operator command. Older images cannot generate codes from Cloud and require an image update; an unavailable command is refused, never replaced with log scraping. Provider failures and unsupported images produce sanitized errors. Local tests cover PostgreSQL transaction boundaries and mocked provider contracts; they do not establish live Fly exec access or image deployment.
